# ウォッチ側の対応：スキャン結果と通報を新しい表に送る（Wi-Fi と BLE）

ウォッチの送り先は **`wifi_reports_v2`（Wi-Fi のスキャンと通報）と `ble_reports`（BLE のスキャン）の2つだけ**です。
**2026-11-22 から、サーバーは今までの `wifi_reports` を読みません。** 新しい表に送るように直るまで、そのウォッチはマップ・入退場・通報に出ません。
テーブルの定義は `supabase/scan_reports.sql` と `supabase/wifi_reports_v2_report.sql`（通報の列）です。

ESP32 は位置の目印として **BLE ビーコン**を出しています（名前が `MAMOTCHI-` で始まる）。現場の **Wi-Fi AP（既設6台）もそのまま使います**。

## 1. 送るもの（新しく足す）

### Wi-Fi のスキャン 1 回ごとに `wifi_reports_v2` へ 1 行（AP が1つも見えなくても送る）

| 列 | 中身 |
|---|---|
| `device_id` | ウォッチの装置 ID（「ユーザー設定」で名前と結び付ける） |
| `scanned_at` | **スキャンした時刻**（ISO 8601、例 `2026-11-19T10:15:30.123+09:00`）。送った時刻ではない。**タイムゾーン（`+09:00` か `Z`）を必ず付ける**（付けないと UTC とみなされ 9 時間ずれる。サーバーは、届いた時刻より 30 秒以上後・1 時間以上前の値を間違いとみなし、届いた時刻で代わりにする） |
| `mac01` / `rssi01` | RSSI がいちばん強い AP の BSSID と RSSI[dBm]（例 `-62`） |
| `mac02` / `rssi02` | 2 番目 |
| `mac03` / `rssi03` | 3 番目（無ければ空） |
| `report` | **通報**。通報している間は `true`、解除したら `false`。サーバーは装置ごとに最新の行の値を見る（マップで赤く光る） |

- この行は通報を運ぶので、**AP が1つも見えなくても送る**（`mac01` などは空でよい）
- 通報ボタンが押されたら、次の Wi-Fi のスキャンを待たずにすぐ1行送ると、通報が早く届く（`mac01` などは直近の結果か空でよい）

### BLE のスキャンごとに `ble_reports` へ 1 行

列は `wifi_reports_v2` と同じです。
- 名前（Complete Local Name）が **`MAMOTCHI-` で始まる**ビーコンだけを対象にする
- 直近のスキャン結果（例: 直近 2〜3 秒）から、RSSI の強い順に上位3つを入れる
- 1つも見えなければ送らない
- 1〜2 秒ごとに送れると、時系列で推定する方式（②④）の精度が上がります

### 共通

- MAC は `AA:BB:CC:DD:EE:FF` の形（大文字・小文字はどちらでもよい。サーバーは大文字に揃えて比べる）
- RSSI は Android の `ScanResult.getRssi()`（BLE）／`ScanResult.level`（Wi-Fi）の値をそのまま入れる
- 並び順は強い順（`rssi01` ≥ `rssi02` ≥ `rssi03`）。違っていても、サーバーが並べ直します

## 2. 今までの `wifi_reports` について

**送らなくてよくなりました**（2026-11-22）。サーバーは読みません。装置の一覧・入退場の判定・通報は、すべて上の2つの表から作ります。
- 装置の一覧: `wifi_reports_v2` と `ble_reports` に行がある装置
- 位置の目印（入退場・エリアに使う上位2つ）: 直近 30 秒以内の BLE が見えていれば BLE、無ければ Wi-Fi
- 通報: 最新の `wifi_reports_v2.report`

今のウォッチが `wifi_reports` に書き込んでいても害はありません（表と列は残してあります）。新しい表だけに送るように直ったら、`wifi_reports` への書き込みを消してください。

## 3. ESP32 のビーコンの中身

| 項目 | 値 |
|---|---|
| 名前 | `MAMOTCHI-<表示名>`（例 `MAMOTCHI-A050`、カメラは `MAMOTCHI-cam-entrance`） |
| アドレス | ESP32 固有の固定アドレス（変わらない） |
| 広告の間隔 | 100ms |
| 送信出力 | +3dBm（全台で同じ） |
| 接続 | しない（スキャンで見えれば十分） |

## 4. Android（Wear OS）で必要なこと

- 権限: `BLUETOOTH_SCAN`（Android 12 以降。位置の計算に使うので `neverForLocation` は付けない）、`ACCESS_FINE_LOCATION`
- BLE は `BluetoothLeScanner.startScan()`。`ScanSettings.SCAN_MODE_LOW_LATENCY` だと拾いやすい
- Android はスキャンの開始と停止を **30 秒に 5 回まで**に制限しています。BLE はスキャンを止めずに続けて、送るときに直近の結果から上位3つを選ぶと安定します
- Wi-Fi のスキャンは Android の制限で回数が少なく（前面でも 2 分に 4 回ほど）、結果が古いことがあります。`ScanResult.timestamp` で、実際にスキャンした時刻を `scanned_at` に入れてください

## 5. サーバーでの使われ方（参考）

位置の計算方法は6つあり、全部を同時に計算しています。どれを使うかはダッシュボードの「位置推定の方式」で選びます（`SPEC.md` §6.3）。

| | 1回のスキャンから | 時間でならす |
|---|---|---|
| ① | 上位2つを 0.8 : 0.2 で配分 | 直近 30 秒・8 回 |
| ② | 上位2つを 0.8 : 0.2 で配分 | カルマンフィルタ（直近 60 秒、人の速さを超える飛びは捨てる） |
| ③ | RSSI の差で、強い2つの AP の間のどこにいるかを出す | 直近 30 秒・8 回 |
| ④ | RSSI の差 | カルマンフィルタ |
| ⑤ | Wi-Fi だけ。上位3つの RSSI すべてに距離減衰の式を当てはめる | カルマンフィルタ |
| ⑥ | Wi-Fi と BLE の両方。BLE は ③、Wi-Fi は ⑤ の計算 | カルマンフィルタ（BLE を重く） |

③④⑤ は RSSI の値を使うので、新しい表が届いて初めて ①② と違う値になります。⑤ は Wi-Fi の3つ目まで使うので、`mac03` / `rssi03` も入れてください。
